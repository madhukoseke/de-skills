## Summary
Handle this as a cross-mode request: architecture design first (DESIGN), then warehouse DDL with partition strategy and cost estimate (WAREHOUSE). Document hand-offs in a data contract and runbook.

## Decision
Sequence the response as: (1) batch ingestion architecture with idempotent landing → staging → mart flow, (2) `CREATE TABLE` DDL with partition-by-date and cluster-by-filter-columns, (3) storage and bytes-scanned cost estimate with validation steps.

## Rationale
Splitting by layer improves clarity and reduces design mistakes (W004, W008). The architecture section defines ingestion reliability, retries, and observability; the model section enforces partition pruning and cost control (W005). Contract tests at the staging→mart boundary prevent silent schema drift (W011).

## Trade-offs
| Option | Pros | Cons | When to Use |
|--------|------|------|-------------|
| Sequential design → model | Clear ownership, traceability, testable boundaries | Slightly longer spec | Cross-mode requests |
| Single blended response | Faster to draft | Easier to miss constraints | Very small changes |
| Stream-first architecture | Lower latency | Higher cost and complexity | Sub-hour freshness SLAs |

## Storage/Cost Estimate
Example: 20M rows/day × 500 bytes/row ≈ 10GB/day landing; 90-day retention ≈ 900GB active partition range. Storage ~$36/month at $40/TB. A partitioned daily query scanning one day (~10GB) costs ~$0.06/run vs ~$5.60/run for a full 900GB scan without partition pruning.
