## Summary
Doubled warehouse spend usually traces to missing partition predicates, new full-scan queries, or concurrency spikes — not "the warehouse got slower." Audit partition pruning first, attribute spend by team/query tag, then apply reservations, compaction, and storage-tier controls.

## Decision
Run an EXPLAIN/dry-run audit on top 20 queries by bytes scanned. Enforce partition pruning on all fact-table reads; add query attribution tags; right-size reservations vs on-demand; schedule compaction for small-file-heavy tables; tier cold partitions to lower-cost storage.

## Rationale
Cost is a feature (W005). Without partition pruning verification, a single BI dashboard can 10× daily spend silently. FinOps attribution makes owners accountable; reservations convert volatile on-demand spikes into predictable credits when baseline load is stable.

## Trade-offs
| Option | Pros | Cons | When to Use |
|--------|------|------|-------------|
| Partition pruning enforcement | Immediate bytes-scanned reduction | Requires query rewrites | Any partitioned fact table |
| Reserved capacity | Predictable cost at steady load | Over-provision risk | Stable 24/7 workloads |
| Result cache / materialized views | Cuts repeated scan cost | Staleness trade-off | High-frequency identical queries |

## Storage/Cost Estimate
If top query scans 5TB/run × 50 runs/day = 250TB/day ≈ **$1,562/day** on-demand at $6.25/TB. Adding `event_date` partition filter to one day (~10GB) drops to ~$3.13/day for that query — ~500× reduction. Attribute savings by `query_tag=team_bi`.
