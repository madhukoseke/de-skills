## Summary
Design a batch RAG ingestion pipeline: land documents in object storage, chunk with versioned embedding contract, upsert vectors idempotently into a managed vector store, and monitor embedding drift plus freshness SLIs.

## Decision
Use batch EL (Airflow/dbt orchestration) → chunking service → embedding model endpoint with pinned model version in the data contract → idempotent upsert to pgvector or Qdrant (team already on Postgres: start pgvector; scale-out path: Qdrant). Enforce embedding schema versioning and DQ checks before index write.

## Rationale
RAG pipelines are still data pipelines (W001, W004, W011). Embedding model/version is a schema contract — silent model swaps cause retrieval quality drift (training-serving skew analog). Idempotent upsert by `(document_id, chunk_id, embedding_version)` prevents duplicate vectors on re-run.

## Trade-offs
| Option | Pros | Cons | When to Use |
|--------|------|------|-------------|
| pgvector (Postgres) | Simple ops if Postgres already exists | Scale limits at high dimension/count | <50M vectors, moderate QPS |
| Qdrant / Weaviate | Purpose-built ANN, filtering | Extra service to operate | High QPS, hybrid search |
| Warehouse vector type | Unified billing | Immature ergonomics | Snowflake/BQ-native shops only |
