## Summary
A clustered-only design for a 2TB table is an anti-pattern. Partition by the primary date filter first, then cluster by high-selectivity columns, and validate with EXPLAIN/dry-run before production.

## Decision
Reject cluster-only design as **not recommended**. Use `PARTITION BY event_date` (or equivalent business date) and cluster/index on `customer_id` and other frequent filter columns. Add a contract test that fails CI when queries omit the partition predicate.

## Rationale
Partitioning is the primary control for scan reduction and predictable cost (Principle W005). Clustering alone cannot prevent full-table scans when queries filter on dates. Without partition pruning, bytes scanned scale with the full 2TB footprint on every query — a fail-loud cost risk, not a silent optimization.

## Trade-offs
| Option | Pros | Cons | When to Use |
|--------|------|------|-------------|
| Partition + cluster | Partition pruning + locality; lower bytes scanned | Requires modeling discipline | Large analytical tables (>100GB) |
| Cluster only | Minor ordering benefit within unsorted data | Weak pruning; high scan cost | Rarely justified at 2TB scale |
| No structure | Fast to create | Unbounded scan cost and latency | Prototypes only |

## Storage/Cost Estimate
Assume 2TB stored at standard tier (~$40/TB/month ≈ $80/month storage). A daily dashboard query scanning the full table without a partition filter reads ~2TB/run. At $6.25/TB scanned, that is ~$12.50/run × 30 runs/month ≈ **$375/month compute** before any optimization. Adding a partition filter on `event_date` targeting one day (~6GB) drops scan cost to ~$0.04/run.
