## Summary
Implement a dbt incremental `orders` model with deterministic merge semantics, explicit `schema.yml` tests, and Airflow orchestration only — with idempotent re-run safety and cost-aware incremental filters.

## Decision
Use dbt `incremental` materialization with `unique_key=order_id`, `incremental_strategy=merge`, and `on_schema_change=append_new_columns`. Add `schema.yml` tests: `not_null`, `unique`, and `relationships` to `dim_customers`. Schedule via Airflow with retry/backoff; fail loud on zero-row loads.

## Rationale
Incremental processing reduces warehouse cost while preserving correctness (W001, W005). dbt owns transform logic and unit/contract tests; Airflow schedules execution only (W008). Tests at the model boundary catch silent data loss before downstream consumers see bad rows (W011).

## Trade-offs
| Option | Pros | Cons | When to Use |
|--------|------|------|-------------|
| dbt incremental + tests | Efficient, testable, idempotent merge | Requires model discipline | Large recurring transforms |
| Full-refresh table | Simple logic | Expensive at scale; higher scan cost | Small or rarely updated tables |
| Raw SQL in Airflow | Fewer tools | Violates separation of concerns | Legacy only |
