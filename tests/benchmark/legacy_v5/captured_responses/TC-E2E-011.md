## Summary
QuotaExceeded at 02:00 UTC on an Airflow DAG usually indicates warehouse slot/quota saturation from concurrent heavy tasks — not a transient network blip. Triage concurrency first, confirm root cause from metrics, apply throttled remediation with retry/backoff, and open an incident record with rollback options if SLA is at risk.

## Decision
Start with structured triage on failing task instances and warehouse quota metrics. Most likely root cause: too many concurrent BigQuery/slot-consuming tasks overlapping the 02:00 UTC batch window. Remediation: reduce `max_active_runs`, stagger heavy tasks, add pool slots, and re-run idempotently after quota clears. If customer SLA is breached, prepare rollback to prior DAG version.

## Rationale
Fast diagnosis reduces SLA impact (W007). Quota errors are fail-loud signals — do not silently retry without backoff, which can worsen saturation (W006). Explicit remediation, risk assessment, and postmortem ownership prevent recurrence. Before finalizing, confirm: Airflow version, which tasks failed, and whether a deploy changed concurrency at midnight UTC.

## Trade-offs
| Option | Pros | Cons | When to Use |
|--------|------|------|-------------|
| Throttle concurrency + stagger | Stabilizes quota quickly | Extends total DAG duration | Quota/saturation incidents |
| Scale up warehouse/reservations | More headroom | Higher cost; may mask bad query design | Sustained growth, budget approved |
| Immediate full re-run all tasks | Simple operator action | Can re-trigger quota failure | Only after concurrency fix applied |
